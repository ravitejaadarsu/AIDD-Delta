**Preflight — the framework must be present.** If `.aidd/framework/` does not exist in this repo, AIDD is not initialized here. STOP and run `/aidd:init` first (it vendors the framework from the installed plugin), or tell the user this repo isn't AIDD-initialized. Do NOT improvise a review, invent phases, or read the PR description and report on it — running the real vendored protocol is the entire point.

Review the pull request named by $ARGUMENTS (an Azure DevOps or GitHub PR id/URL, or a local `<base>..<head>` ref pair) per `.aidd/framework/protocol/pr-review.md`. Read the `pr_review:` block in `.aidd/constitution.md` for this repo's platform, invariants files, dimension-specialist roster, redline patterns, allowlist file, and ticket linkage — every key has a default, so an absent block is not a blocker. Resolve the rigor mode from the merge-base diff's path set (`.aidd/framework/protocol/rigor-modes.md`) and every dispatch through `.aidd/framework/protocol/dispatch.md` rows `PR review 1a/1b/1c/2/3/4` — never by judgment.

Then run the five phases: **phase 0** fetch the PR's source and target from the platform (`az repos pr show` / REST for Azure DevOps, `gh pr view --json` for GitHub), compute `git merge-base <target> <source>`, and record the resolved BASE and HEAD SHAs as evidence — the PR description is a claim, never ground truth; **phase 1** fan out finders (one `pr-file-reviewer` per changed source file, helper bundled with its component, trivial/cosmetic and E2E/config batched into sweep agents, plus the dimension specialists the config names); **phase 2** send EVERY finding to `.aidd/framework/roles/adversarial-verifier.md` in `mode: pr` — never to the agent that raised it — which answers why it is a real problem and when it manifests, refutes what it cannot trace, defaults to refuted when uncertain, and sets the severity; **phase 3** dispatch the `pr-cross-cutting-reviewer` over the whole feed for shared-package impact, platform-only violations, dead paths, constant drift, missing cross-boundary tests, and dedup; **phase 4** dispatch the `pr-comment-validator` as the final gate — a comment that fails validation is dropped, not softened.

Every review states an explicit `PASS | FAIL | N/A (why)` verdict on all three acceptance-bar items — **additive**, **non-breaking** (proven by tracing the inactive path in the code), **no hardcodes** (redline scan, allowlist untouched, escape hatches, and an honest assessment of whether the tests verify real behavior). A report missing any of the three is incomplete by format. Never flag a shared-code behavioral change without grepping the actual runtime consumer first.

Report to the user: conclusion and confirmed findings only, in `.aidd/framework/protocol/progress.md` lines — never raw agent dumps. **Nothing is posted to the PR without explicit human approval in this run**, in both autonomy modes. Emit the post-ready comment list, say how many comments it holds, and stop.
